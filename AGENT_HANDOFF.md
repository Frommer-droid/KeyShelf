# KeyShelf — состояние проекта

Обновлено: 2026-10-02. Статус: подготовка полного релиза 0.3.0.

## Текущая задача

Подготовить версию 0.3.0 с мини-режимом, исправлением дрожания карточек,
русским установщиком и обновлённой portable-папкой. После локальной сборки,
проверок, dry-run и private backup дождаться отдельного разрешения на GitHub push.

## Реализовано

- Мини-режим: общий поиск по всем записям; пустой запрос не показывает список.
  Результаты раскрываются аккордеонами; поля и 2FA копируются квадратными кнопками.
- «Мини» стоит последней справа в верхнем ряду; «Макси» встроена в строку поиска.
- Режим и отдельная геометрия окон сохраняются. После перезапуска сначала
  разблокировка в полном интерфейсе, затем восстановление выбранного режима.
- Закрытие любого режима, включая заблокированное окно, скрывает его в трей,
  если трей доступен. Возврат в мини сохраняет запрос и раскрытые карточки,
  фокусирует поиск. Запрос не записывается на диск; блокировка очищает обе панели.
- Устранено дрожание карточек: размеры задаются до вставки в layout, очистка
  поиска не запускает лишний refresh, выбор сервиса обрабатывается один раз.
- README RU/EN, версия EXE/Inno, release notes и скрытый runtime smoke обновлены.
  Иллюстрация docs/mini-mode.png содержит только вымышленные данные.

## Проверки исходников

- Полный native Windows suite после реализации мини: 125 passed.
- После переноса кнопки и изменения копирования: 6 связанных тестов и native
  smoke прошли, включая 2FA и все четыре типа записей.
- Релизные проверки: 28 тестов payload/runtime policy, mini, copy и service filters
  прошли; Ruff, pip check и source runtime smoke прошли.
- OSV scan точного requirements-lock.txt: 28 пакетов, известных уязвимостей нет.
  Recursive scan requirements-файлов сообщил старые транзитивные версии из
  метаданных зависимостей; они не совпадают с установленными версиями в lock.
- Offscreen-среда не предоставляет системный трей; полная проверка выполнена
  с настоящим Windows Qt backend.
- tests/verify_launcher.py учитывает скрытие заблокированного окна в трей и
  завершает только своего потомка. Helper не запускался, чтобы не менять
  пользовательские настройки; поведение покрыто native tray tests и smoke.

## Правила релиза

- Исходная точка: main, dcfe4da, tag 17; предыдущий локальный релиз v0.2.1/tag 16.
  Новый release commit должен получить v0.3.0 и следующий числовой tag 18.
- Сборка только из .venv с минимальным доверенным PATH. Spec запрещает чужие
  binary origins; полный набор MSVC DLL должен совпадать с PySide6 runtime.
  Сохранить COLLECT и audit перед удалением build work; проверить frozen smoke.
- Готовую корневую сборку проверять до отдельного pre-build удаления.
  Portable обновлять с сохранением settings.json/startup.log и других данных.
- Приложение, portable GUI и настоящий installer во время релиза не запускать.
  Разрешён скрытый неинтерактивный runtime smoke на синтетическом хранилище.
- Portable-архив не запрошен. Полезные release reports сохранять в .verification;
  одноразовые caches/work убирать после последней проверки.
- Лицензия GPL-3.0, PyKeePass тоже GPL-3.0. Общий MIT-шаблон неприменим.
- Native audit новых версий хранится в ignored .verification. Исторический
  docs/native-runtime-audit.json относится к 0.2.1.
- ShareMyApp: карточки KeyShelf нет; создание карточки не запрошено.

- GitHub остаётся private. На старте main и tag v0.2.0 указывают на
  333fc1f682ea81736666096953a96316e05be0aa; локальная история отличается от orphan remote.
- Для нового orphan dry-run/push использовать штатный helper с
  PruneRemoteTags=false, PruneRemoteBranches=false, PruneOldReleases=false.
  Числовые локальные tags не публиковать. Visibility не менять.
- Старый remote v0.2.0 сохраняет исторический внутренний handoff; private выпуск
  с сохранением старых refs не очищает его. Перевод в public требует отдельного
  решения и проверки старых refs/assets.
- Предыдущие приватные backup и release archive сохраняются вне tracked дерева.
  Перед запросом push выполнить dry-run и bk, сообщить результат пользователю.
- Реальный push допустим только после отдельного подтверждения после dry-run.
